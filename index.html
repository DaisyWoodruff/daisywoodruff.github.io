¶负载均衡损失(Auxiliary Load Balancing Loss)

一方有难八方看戏
(1,6号专家学到了几乎所有的知识)

-> 让每个专家的负载尽量均衡

loss=αN⋅∑i=1NfiPiloss = \alpha N \cdot \sum^N_{i=1} f_i P_i loss=αN⋅i=1∑N​fi​Pi​

α\alphaα 是超参数, N是专家数量, fif_ifi​是第i个专家的实际负载比例, PiP_iPi​是路由概率期望

主观的直觉–不可能是所有专家的能力都是一样的, 有的专家有更好的能力

要求更多考虑不同设备负载均衡

把 α2\alpha_2α2​ 设置的较大,α1\alpha_1α1​ 设置的较小–考虑硬件的实际限制

bib_ibi​ 的调整是在线且基于统计的
训练的时候砍掉Auxiliary Loss没问题, 但是推理的时候如果专家收到了严重偏离分布的序列, 专家会不知所措
推理阶段需要更强大的平衡机制–引入Complementary Sequence-wise Auxiliary Loss

(注意顺序是从下向上…)

左边(传统MoE): 先做Softmax, 再取TopK
右边(Deepseek改进): 先做Sigmoid, 取TopK, 最后再做归一化(Normalize)

核心目的: 解决"特征塌陷"和数值稳定性问题–保证被选中的专家权重之和恒为1
(原本截取过的softmax的和一定不为1, 改进版对结果做一次softmax就一定为1了)

改进原理: 解耦"打分"和"竞争"
先对每个专家进行独立考核,(a得高分不影响b得高分) – 更加适配Fine-Grained Expert(细粒度专家)场景, 因为一个token确实需要同时激活多个高相关性的专家

¶踩坑实录

Obsidian 图床方案复盘：腾讯云 COS + PicGo

¶目标

在 Obsidian 里粘贴图片后自动上传，笔记里使用外链图片，减轻同步压力（Remote Save / 坚果云 WebDAV），同时保证链接长期稳定可用。

  • 个人笔记，图片总量预计 < 1GB；月访问流量 < 10GB。
  • 国内访问为主。
  • 不想折腾自定义域名/SSL 证书。
  • 之前 Imgur 插件的 Client ID/OAuth 路线受阻，决定换平台。

¶最终方案

  • 图片存储：腾讯云 COS（对象存储）
  • 上传工具：PicGo（COS v5）
  • Obsidian 引用方式：Markdown 外链 ![](https://...)
  • 缓存优化：通过 COS 控制台批量设置对象的 Cache-Control 响应头（不写脚本）
  • 同步策略：只同步 Markdown 文本（附件不上同步或大幅减少），图片走公网访问

一句话：文本走同步，图片走对象存储。

¶探索路线（思维地图）

¶1) 用工程拆分降低复杂度

  • 同步系统（WebDAV/坚果云/Remote Save）对二进制和高频请求不友好 → 让它只搬 Markdown 文本。
  • 大文件（图片）交给更擅长做静态资源分发的系统（对象存储） → COS。

¶2) 寻找和配置图床

¶1. Imgur挂了

  • IImgur 的 addclient 入口目前无法使用（跳转首页），OAuth 也不稳定；疑似政策/接口调整. 但是这已经调整半年了,我觉得就是政策收紧.
  • SM/MS则是直接停止了新用户注册
  • 结论：不死磕，换平台。

¶2) 判断需求本质

  • 我需要的是“稳定可用的静态资源链接”，本质是 存储 + 公开读取 + HTTPS。
  • 所谓“图床”其实就是：能给出长期稳定的 URL。

¶成功落地步骤

¶A. COS 侧配置

  1. 创建存储桶（Region 选国内，例如北京 ap-beijing）。

  2. 确保图片可长期显示：

    • 方案选择: 公有读私有写（图片对象要允许公网读取）。
    • 只要链接要给 Obsidian/博客展示，就不能依赖“会过期的签名 URL”。

经验：“完全私有 + 永久在线可展示”天然矛盾。

¶B. PicGo 配置（COS v5）

  1. PicGo 图床选择：腾讯云 COS（v5）

  2. 填写关键参数：

    • SecretId / SecretKey（自己的腾讯云就只用来做图床一件事,于是直接用主账号管理了）(注意SecretKey只显示一次, 记得存下csv并妥善保存)
    • AppId(注意不是桶ID, 这个是在调用api的时候用到的)
    • Bucket：注意 v5 要写成 bucketname-appid(直接复制不要手动抄)
    • Region：例如 ap-beijing(同理,直接复制不要手动抄)
    • Path：建议设置一个统一前缀（例：obsidian/2026/01/ 或 img/）

  3. 上传测试：PicGo 返回一个 https://...myqcloud.com/...png 的链接, 在桶里能看到文件, 将链接粘贴到obsidian里能正常显示图片

¶C. Obsidian 接入

  • Obsidian 使用支持 Image_auto_upload 的插件,让其在粘贴时自动调用 PicGo 上传并把返回链接写入 Markdown。

  • 成功标志：复制后出现短暂的上传界面, 然后就和粘贴图片附件一样可以正常浏览

¶Remote Save 和 坚果云 的问题

  • WebDAV 常见 503，多半是服务端限流/保护导致短时间大量 PROPFIND/GET/PUT 很容易触发。

  • 我把图片从同步链路里拿掉 → 同步只处理 .md 文本：

  • 少让服务器频繁比对二进制文件

  • 同步系统压力下降，稳定性上升。

¶缓存与成本：我做了什么、理解了什么

¶1) 缓存结论（够用版本）

  • Obsidian 桌面端本质上用的是浏览器渲染机制，外链图片走 HTTP 缓存。

  • 不是“每次打开必然完整下行”，但可能会发生：

    • 首次加载：200 下载（产生下行）
    • 之后：命中缓存（不下行）或 304 校验（请求次数增加、下行很小）

  • 缓存是否有效，取决于图片响应头（尤其 Cache-Control）和本地缓存是否被清理。

¶2) 我采用的缓存策略（不写脚本）

我没用脚本，直接走 COS 控制台批处理：

操作路径（概念）：

  • COS 控制台 → 文件列表 → 多选对象 → 批量操作 → 设置自定义 HTTP 头（Cache-Control）

Cache-Control 推荐值（适合“不可变文件名”的图床）：

  • public, max-age=31536000, immutable（缓存 1 年 + 资源不可变）

为什么适合我：

  • 我上传的文件名是时间戳/随机串（不可变），几乎不会“同名覆盖更新”。 因此可以大胆长缓存，减少反复校验请求。

如果未来我会“同名覆盖”，那就不要用 immutable，或者缩短 max-age。

¶3) 计费直觉（够用版本）

  • 主要费用通常来自 公网下行流量。
  • 我估算：存储 <1GB + 月下行 <10GB → 不值得上 CDN（复杂度 > 收益）。
  • 所以选择：直接 COS 默认域名，就够了。

¶SSL/HTTPS：我最终的判断

  • 我不需要“自己搞 SSL 证书”，因为 COS 默认域名自带 HTTPS（用 https:// 即可） 只有当将来绑定自定义域名（比如 img.xxx.com）时，才需要额外处理证书。
  • 现在的当务之急是打好工作流, 然后赶紧开始产出文档本身.

¶常见问题与排查清单（未来踩坑时先看这里）

  1. Obsidian 里显示裂图/403
  • 桶或对象权限是否允许公网读取？
  • 是否不小心用了签名 URL（会过期）？
  • 链接是否是 https://？
  1. 上传成功但链接打不开
  • Region/Bucket 填错（尤其 v5 bucket 格式 name-appid）
  • 链接拼接域名错误
  • 对象是否被误删/生命周期规则清理
  1. 坚果云 WebDAV 又 503
  • 同步频率太高 / 文件太多
  • 减少自动同步，拉大间隔
  • 把大附件继续留在 COS，不走 WebDAV

¶经验

  1. 遇到平台侧故障/入口变化，不要死磕：验证现象后果断换路线。
  2. 把问题抽象成“我需要长期稳定 URL 的静态资源”，就不会被“图床插件”绑架。
  3. 工程拆分：文本同步 ≠ 附件同步。二进制交给对象存储，能显著提高整体可靠性
  4. 先跑通，再优化：先让链接可用，再考虑缓存头、版本控制、路径规划等增强项。
  5. **文档读不懂不是我菜：我需要的是“任务地图”，不是百科全书。
  • 上传前做图片压缩/去 EXIF（省流量、提隐私）
  • 未来如果博客流量变大，再考虑 CDN（现在不用）
  • 后续有空换成子账号密钥，只给 COS 该桶写权限。

¶使用一个周后反馈

  • 顺滑, 图片几乎无感地转化成云端存储, 没有遇到其他问题. 给同学配置也很方便
  • 另外有个之前没想到的惊喜:
    • 图片可以很方便的在不同仓库之间引用和迁移, 只需要修改云端的源文件就可以无痛更改所有文档中的引用
  • 费用几乎可以忽略不计, 正常作为笔记使用, 一天1分钱
